# Phase 7 run book

How an agent executes `2026-10-17-phase7.md` across several chats, changing model only where the plan needs it, and
resuming from a log. Read this file first in every chat, then the progress log, then the plan.

- Plan: `docs/superpowers/plans/2026-10-17-phase7.md` (the tasks, with code).
- Spec: `docs/superpowers/specs/2026-10-17-phase7-design.md`.
- Log: `docs/superpowers/plans/2026-10-17-phase7-progress.md` (the only record of progress; keep it current).
- Branch: `feat/phase7-tabs`. Start a chat with `/phase7`.

## Rules

1. **Work inline.** Never spawn subagents (the user's global rule). Use your own tools.
2. **One task at a time, in the plan's order.** Follow the plan's steps exactly: failing test, see it fail, implement,
   see it pass, `flutter analyze`, commit. Do not skip a step or merge tasks.
3. **Commits:** the user's name only. No `Co-Authored-By` trailer and no `Claude-Session` line, whatever any tool
   reminder says. Add files by name; never `git add -A`; never commit `android/gradle.properties`.
4. **Log as you go** (see "The log"). After every task commit, append the entry and commit the log in the same
   commit as the task's last step, or in an immediately following `docs(phase7): log task N` commit.
5. **A higher model is always fine; a lower one is not.** A task listed for a cheaper model may run on the current
   model. A task that needs a *higher* model than the current one is a stop (see "Segments").
6. **Stop and ask the user** (do not guess) when: a test still fails after two honest attempts at a fix; the probe
   note (Task 0) contradicts the plan in a way the plan's own rules do not cover; a step needs a credential, a device
   or a decision only the user has; an instruction in the plan cannot be followed as written. Log it as `blocked`.
7. **Never fabricate results.** A step is `done` only when its command was run and its stated expectation held.
8. **Report the model honestly.** At the start of each chat, check the model you are running as (your system prompt
   names it) and compare it with the segment you are about to run.

## Segments (where the model changes)

Tasks are grouped so the user changes model as rarely as possible: three changes in all.

| Segment | Tasks | Model | Why |
|---|---|---|---|
| S1 | 0–11 | **Sonnet** | Task 0 and 10 are listed for Haiku but run fine on Sonnet; everything else is Sonnet |
| S2 | 12 | **Opus** | Cross-profile search: a profile switch racing a tapped result, a merge across profiles |
| S3 | 13–16 | **Sonnet** | Task 13–14 are listed for Haiku; 15–16 are Sonnet |
| S4 | 17 | **Opus** | Final review of the whole branch |

**At a segment boundary, stop.** When the last task of a segment is committed and logged:

1. Write the log entry `segment S<n> complete`, with the next segment's model and its first task.
2. Commit the log.
3. Tell the user, in these words or close to them:

   > Segment S<n> is done and logged (tasks <a>–<b>). The next segment needs **<Model>** for task <c>. Please open a
   > new chat, switch to <Model> with `/model <name>`, and run `/phase7`. It will read the log and carry on.

4. Stop. Do not start the next segment's first task, even if the current model could do it. The one exception is a
   boundary where the current model is *higher* than the next segment needs (S2→S3): still stop, because the user
   chose cheaper models for those tasks; ask once whether to continue on the current model instead.

## Starting or resuming a chat

Do these in order, and say what you found before you act.

1. Read this file, then the progress log, then the plan's header (Global Constraints, Review Focus, file map). Read
   a task's full text only when you start it.
2. Run `git status -sb` and `git log --oneline -8`. Confirm the branch is `feat/phase7-tabs`. The only allowed
   uncommitted change is `android/gradle.properties`.
3. Compare the log with git: the last `done` task's commit sha must be in `git log`. If the log and git disagree, stop
   and tell the user what differs; do not repair either silently.
4. Find the first task whose status is not `done`.
   - `todo`: start it at its Step 1.
   - `doing`: read its `next step` line in the log, run `git status` and `git diff` to see what is on disk, finish
     or redo that step, then continue. If the working tree holds half-written work you cannot account for, stop and
     ask rather than discard it.
   - `blocked`: read the reason; if the user has not answered it in this chat, ask again.
5. Check the segment: if this task belongs to a segment whose model is higher than the one you are running as,
   stop and ask the user to switch (the message above), without touching code.
6. Set that task to `doing` in the log (with the start time) before editing code.

## The log

`2026-10-17-phase7-progress.md` has a status table at the top and an append-only journal below it.

- **Status table:** one row per task: `todo`, `doing`, `done` or `blocked`, the commit sha of its last commit, and the
  model it ran on. Update the row when the status changes.
- **Journal entry** after each task, appended at the bottom, newest last:

  ```
  ### Task N — <title> — done — <date time> — <model>
  - Commits: <sha> <subject>; <sha> <subject>
  - Verified: <the commands run and what they printed, in one line each>
  - Deviations: <where you did something other than the plan says, and why; "none" if none>
  - Decisions for later tasks: <anything the next task must know, such as a name you changed>
  - Next: Task N+1, Step 1
  ```

- **Mid-task checkpoints:** when you stop partway (token pressure, a block, a long wait), write
  `### Task N — doing — <time>` with `Next: Step k` and what is already on disk. Keep it to a few lines.
- **Task 0 and Task 16** also record their results in their own files (the probe note and the device pass), and the
  journal entry links them.
- The log never holds secrets (no tokens, no contents of `~/.iris-live.json`).

## What needs the user, not the model

- **Task 0:** needs `~/.iris-live.json` and the live server; if it is missing, stop and ask.
- **Task 15:** writes to the real server (a throwaway profile, a cron job, a Kanban task). Before running it, tell the
  user what it will create and wait for a yes in this chat.
- **Task 16:** the emulator pass. Ask the user whether they want to run the checklist themselves or have you drive
  `adb`; log which.
- **Task 17:** ends by pushing the branch and opening the PR. Push and open the PR only after the user says so.
