# GenUI — Implementation Plan

> **For agentic workers:** execute with superpowers:executing-plans, inline. Never spawn subagents. Steps use checkbox
> (`- [ ]`) syntax for tracking. Phase 0 is a gate: do not start Phase 1 until its findings are written into the spec.

**Goal:** Hermes replies in Iris with native, personal UI — displays and reply kits designed from the person's own
work — through the `hermes-iris` plugin and its `iris-genui` skill, and only in Iris.

**Architecture:** server package `server/hermes-iris/` (Hermes plugin: tools, hooks, dashboard routes, bundled skill,
file store). App: `lib/data/genui/` (REST + parsing), `lib/features/genui/` (settings, controller, catalog/renderer,
reply kit, study and displays screens), with small hooks into the chat controller, transcript and capabilities.
`package:genui` is used only for `SurfaceController`/`Catalog`/`DataModel`/`Surface`, behind
`lib/features/genui/render/`.

**Spec:** `docs/superpowers/specs/2026-10-31-genui-design.md` (decisions D1–D9, catalog, security, risks).

**Tech Stack:** Flutter 3.41.6 / Dart 3.11, Riverpod 3 (hand-written providers), new: `genui` (exact pin, ≥ 2 weeks
old, chosen in Task 2.1), `json_schema_builder` if `genui` needs it directly. Server: Python ≥ 3.11 (Hermes's),
FastAPI (already in the dashboard), pytest.

## Global Constraints

- Branch `feat/genui` (this plan); each phase may branch off it as `feat/genui-pN` and merge back.
- Commits under the user's name only: no `Co-Authored-By`, no `Claude-Session` line. Add files by name; never
  `git add -A`; never commit `android/gradle.properties` or `store/screenshots/`.
- Every Flutter task ends with `flutter analyze` → `No issues found!` and its tests green; the last task of a phase runs
  the full `flutter test` (excluding `--tags live`). Every server task ends with `pytest server/hermes-iris` green.
- Live tests against hermes.shreyaskamat.in wait ≥ 240 s per turn and re-flag the session after reconnect.
- Every plugin route takes `?profile=`; every Iris call to it goes through `DashboardChat._scoped`-style scoping.
- Nothing personal (profile, templates, samples) is injected into a turn before the person approves it in Iris.
- Never log surface data, action contexts, or study samples unredacted (`IrisLog.redact`).
- Copy is British English, matches `docs/design-language.md`; no raw error codes in a primary line.

## Phase 0 — Live probe (gate)

Answer, on the user's Hermes 0.18.x, the questions the design depends on. Write results into the spec's "Research"
section and adjust D2/D3 before Phase 1.

- [ ] **0.1 Minimal probe plugin.** `server/hermes-iris-probe/` with: a no-op tool `iris_probe(payload)` returning its
  input length; a `pre_llm_call` hook returning `{"context": "[iris-probe]"}` only when a module-level set contains the
  session id; `pre_tool_call` logging kwargs; a dashboard `plugin_api.py` with `GET /hello` and
  `POST /sessions/{id}/flag`. Install by copying to `~/.hermes/plugins/`, `hermes plugins enable iris-probe`, restart.
- [ ] **0.2 Auth.** From outside the server: `GET https://hermes.shreyaskamat.in/api/plugins/iris-probe/hello` with and
  without the dashboard cookie and with Cloudflare Access headers if used. Record whether it is protected.
- [ ] **0.3 Tool event payloads.** Ask the agent to call `iris_probe` with 1 KB, 8 KB and 32 KB payloads. Capture the
  raw `tool.start` / `tool.complete` events in Iris's debug log: are args complete, truncated (`args_text` preview), or
  absent? Is `tool_id` present to match start/complete?
- [ ] **0.4 Hook context.** Flag a session, send a turn, then read `/api/sessions/{id}/messages`: is `[iris-probe]`
  stored in the user row? Does `session_id` in the hook equal the runtime id Iris has, or the stored id?
- [ ] **0.5 Flag lifetime.** Reconnect the socket, `session.resume`, send again: does the flag (keyed by which id)
  survive? Decide: key by stored session id if the hook sees it.
- [ ] **0.6 History rows.** In stored history, how does an `iris_probe` tool call appear (role, name, args, result)?
  Check `history_parser.dart` handles it.
- [ ] **0.7 Platform field.** What `platform` value do hooks receive for dashboard WS sessions vs Telegram/CLI?
- [ ] **0.8 Write up** in the spec; delete the probe plugin from the server; commit the spec change.

## Phase 1 — `hermes-iris` server package

- [ ] **1.1 Skeleton.** `server/hermes-iris/{plugin.yaml,__init__.py,dashboard/manifest.json,dashboard/plugin_api.py}`,
  `pyproject.toml` (pytest only), `README.md` with install/enable/upgrade steps. `GET capabilities` returns
  `{version, a2ui: "v0.9", catalog_ids: [...], features: [...]}`. Test: route test with FastAPI `TestClient`.
- [ ] **1.2 Auth.** Per Phase 0.2: either rely on the dashboard auth (documented, with a test that fails if the
  manifest changes) or verify the session cookie in a router dependency. Test: unauthenticated request → 401.
- [ ] **1.3 Store.** `genui/store.py`: per-profile dir `~/.hermes/iris/<profile>/` with `profile.json`,
  `templates/<id>.json`, `surfaces/<session>/<surface>.json`, `usage.jsonl` (rotated at 1 MB); atomic write
  (temp + rename); path components validated (`^[A-Za-z0-9_-]{1,64}$`). Tests: round trip, traversal rejected.
- [ ] **1.4 Catalog + validator.** `catalog/v1.json` (initially hand-written; Task 2.4 makes Dart the source and adds
  the drift test). `genui/validate.py`: version, exactly one envelope key, one `root`, every child id exists, no
  cycles, depth ≤ 8, ≤ 60 components, ≤ 16 KB, props match the item schema, `{path}` strings are JSON pointers. Return
  errors as short model-readable lines. Tests: one per rule, plus the spec's order-status example.
- [ ] **1.5 Session flag.** `POST sessions/{id}/genui` → in-memory map (+ file for restarts) of flagged ids with
  `catalog_version`/`templates_rev`. Key choice from Phase 0.5. Tests.
- [ ] **1.6 `iris_ui` tool.** Args per spec; `template`+`data` expands via `genui/templates.py` (data validated against
  the template's schema); validates; stores; returns `{surface_id, rev, ok}` or `{ok:false, errors}`. Requires
  `fallback`. Tests incl. update of an existing surface (rev increments) and `deleteSurface`.
- [ ] **1.7 Guards.** `pre_tool_call` blocks any `iris_*` tool in unflagged sessions with a one-line reason;
  `transform_tool_result` trims `iris_ui` results to the receipt. Tests with fake kwargs.
- [ ] **1.8 Turn context.** `genui/context.py` builds ≤ 2,500 chars: rules, catalog digest, approved templates index;
  `pre_llm_call` returns it for flagged sessions only (none for others). Snapshot test of the text; budget test.
- [ ] **1.9 Surface routes.** `GET surfaces/{session}/{surface}`, `GET surfaces/{session}`. Tests.
- [ ] **1.10 Skill `iris-genui`.** `SKILL.md` (when to render vs plain text, D7 text-complete rule, one surface per
  idea, prefer templates, reply kits for decisions, update rather than re-create, never put secrets in data), plus
  `references/catalog.md` (generated from `catalog/v1.json` by a script), `references/patterns.md` (8–10 worked A2UI
  examples on the Iris catalog). Register with `ctx.register_skill`.
- [ ] **1.11 Live check.** Install on the user's server, flag a session with `curl`, ask for "a status card for my cron
  jobs" over the dashboard WS, confirm a stored, valid surface and a text reply. Log results.

## Phase 2 — Rendering surfaces in Iris

- [ ] **2.1 Spike + pin.** Add `genui` (exact version, ≥ 2 weeks old) on a throwaway branch; render the spec's
  order-status example in a widget test via `SurfaceController.handleMessage` + `Surface`. Check: no Material-only
  assumptions that fight Iris theming, works with Riverpod/no `Conversation`, iOS + Android build, app size delta.
  **Decision point:** keep `genui` or write `render/a2ui_renderer.dart` (four messages, flat components, path bindings,
  templates). Record in the spec.
- [ ] **2.2 Capability.** `ServerCapability.irisGenui('/api/plugins/iris/capabilities', 'Generative UI')`; parse
  `version`, `catalog_ids`. Tests in `capabilities_test.dart`.
- [ ] **2.3 Models + API.** `lib/data/genui/genui_models.dart`, `genui_api.dart` (scoped profile), `genui_parser.dart`
  (`iris_ui` tool events → `UiSurfaceRef`; `<iris-action>` strip/parse). Unit tests with recorded Phase 0 payloads.
- [ ] **2.4 Iris catalog, part 1.** `render/iris_catalog.dart`: layout + text & data items (`Column`, `Row`, `Card`,
  `Section`, `Divider`, `Text`, `Markdown`, `KeyValue`, `Stat`, `StatRow`, `StatusPill`, `Table`, `List`, `Timeline`,
  `Checklist`, `Progress`, `CodeBlock`, `Image`, `Link`) on `lib/design` tokens. A test exports the schemas to
  `server/hermes-iris/catalog/v1.json` and fails when the checked-in file differs.
- [ ] **2.5 Surface view.** `render/surface_view.dart`: loading shimmer, fallback text on validation/render error,
  "can't show this" chip for unknown components, max height with "Show all", semantics labels. Golden tests light/dark
  for each catalog item (follow the existing goldens setup).
- [ ] **2.6 Transcript integration.** `UiSurface` item; `ChatController` maps `iris_ui` tool events and stored history
  rows to it (fetching full messages by id when args are partial); `TranscriptEntry` renders it inside the assistant
  block. Hide hook context in user rows if Phase 0.4 found it stored. Tests with a fake backend.
- [ ] **2.7 Session flagging.** `GenUiController`: on chat open/create/resume/reconnect with GenUI enabled and the
  capability present, `POST sessions/{id}/genui`. Settings toggle (per server + profile) in `PreferencesStore`, off by
  default; settings section shows plugin status and install help when missing. Tests.
- [ ] **2.8 Phase check.** Full `flutter test`, `flutter analyze`, debug APK; live: ask for a status card, see it render
  on the emulator (memory: wait ≥ 240 s; emulator storage gotchas).

## Phase 3 — Actions, inputs and reply kits

- [ ] **3.1 Catalog, part 2.** `Tabs`, `Expander` (local), charts (`Sparkline`, `LineChart`, `BarChart`, `Donut` as
  painters), `Diff`. Goldens.
- [ ] **3.2 Inputs.** `Button`, `ChoiceChips`, `TextField`, `Slider`, `Toggle`, `DatePicker`, `Stepper`,
  `ApproveReject`, `Submit`, all writing to the surface data model; platform-adaptive via `lib/design/platform`.
- [ ] **3.3 Action → message.** An A2UI `action` builds a visible sentence (from the component's `label`/action
  `name` + context summary) plus `<iris-action>{…}</iris-action>`; submitted through `ChatController` (respects busy
  mode and the queue). Transcript hides the block. The skill documents how to read it. Tests.
- [ ] **3.4 Reply kits.** `placement: "reply_kit"` surfaces dock above the composer (`reply_kit.dart`), dismissible,
  replaced by the next kit, cleared when the person types. Tests + goldens.
- [ ] **3.5 Surface updates.** `iris_ui` on an existing `surface_id` updates in place (rev); older revs in history show
  the latest rev with a "updated" tag. Tests.
- [ ] **3.6 Live check** of an approve/hold reply kit end to end.

## Phase 4 — Study: profile and personal displays

- [ ] **4.1 Server: profile + templates.** `iris_profile_get/propose`, `iris_template_list/propose` tools; template file
  format `{id, name, when, data_schema, components, sample_data, status: proposed|approved|retired, rev}`; template
  validation = component validation + sample data against schema. `GET/PUT profile`, `GET/PUT/DELETE templates/{id}`.
  `pre_llm_call` includes only `approved` templates. Tests.
- [ ] **4.2 Skill procedure `/iris-study`.** `references/study.md`: gather (memory, `session_search` over ~90 days,
  skills, cron, Kanban, toolsets), infer profile, propose 3–8 templates and 2–4 reply kits with redacted sample data
  from real turns, summarise in text. Include anti-patterns (no secrets, no one-off templates, no duplicate shapes).
- [ ] **4.3 Iris: start study.** Settings ▸ Generative UI ▸ "Study my work": explains what will be read, creates an
  "Iris setup" session, sends `/iris-study`, shows progress (reuses chat streaming), then opens review.
- [ ] **4.4 Iris: review screen.** `study_screen.dart`: profile as editable chips; each proposed template rendered
  live with its sample data; Keep / Rename / Drop; "Keep all"; writes via `PUT`. Goldens + widget tests.
- [ ] **4.5 Iris: Displays screen.** `displays_screen.dart`: approved templates with preview, rename, retire, "Re-study";
  shows a badge when refinements are pending.
- [ ] **4.6 Live check:** run study on the user's real server; review; confirm the next turns use approved templates.

## Phase 5 — Learning loop

- [ ] **5.1 Signals.** Iris posts `used` (surface visible ≥ 2 s), `expanded`, `dismissed`, and "Not useful" (long-press
  menu on a surface, next to existing message actions). Batched, best-effort. Tests.
- [ ] **5.2 Usage log.** `post_llm_call` appends `{ts, session, templates_used, surfaces}` to `usage.jsonl`. Tests.
- [ ] **5.3 `/iris-refine`.** Skill procedure: read usage + feedback, propose edits/new/retire as `proposed`. Optional
  weekly cron created from Iris through the existing cron UI/repository (off by default).
- [ ] **5.4 Iris:** refinement proposals reuse the review screen in "changes" mode (before/after preview).

## Phase 6 — Polish, demo, release

- [ ] **6.1 Demo mode.** `demo/` scripted surfaces, a reply kit and a fake study result so demo mode (and store
  review) shows GenUI without a server.
- [ ] **6.2 Export & search.** Chat export uses each surface's `fallback`; search indexes fallback text.
- [ ] **6.3 Accessibility.** Semantics for every catalog item; text scale 200 %; screen reader pass on both platforms.
- [ ] **6.4 Device pass** (Android + iOS, light/dark, 320 pt width) with screenshots in
  `docs/superpowers/plans/2026-10-31-genui-device/`, following earlier device-pass docs.
- [ ] **6.5 Docs.** `server/hermes-iris/README.md` install guide, README feature section, CHANGELOG, privacy-policy
  note (study reads the person's own server data; nothing leaves their server).
- [ ] **6.6 Release** the plugin (tag `hermes-iris-v0.1.0`) and merge `feat/genui` to `main` via PR.
