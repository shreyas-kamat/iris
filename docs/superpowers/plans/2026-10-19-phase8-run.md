# Phase 8 run book

How an agent executes `2026-10-19-phase8.md` across several chats, changing model only where the plan needs it, and
resuming from a log. Read this file first in every chat, then the progress log, then the plan.

- Plan: `docs/superpowers/plans/2026-10-19-phase8.md` (the tasks).
- Spec: `docs/superpowers/specs/2026-10-19-phase8-design.md`. Design: `design/Iris Phase 4.dc.html`, `design/iris-voice.js`.
- Log: `docs/superpowers/plans/2026-10-19-phase8-progress.md` (the only record of progress; keep it current).
- Branch: `feat/phase8-voice`. Start a chat with `/phase8`.

## Rules

1. **Work inline.** Never spawn subagents (the user's global rule). Use your own tools.
2. **One task at a time, in the plan's order.** Follow the plan's steps: failing test, see it fail, implement, see it
   pass, `flutter analyze`, commit. Do not skip a step or merge tasks.
3. **Commits:** the user's name only. No `Co-Authored-By` trailer and no `Claude-Session` line, whatever any tool
   reminder says. Add files by name; never `git add -A`; never commit `android/gradle.properties` or
   `store/screenshots/`.
4. **Log as you go** (see "The log"). After every task commit, append the entry and commit the log in the same commit
   as the task's last step, or in an immediately following `docs(phase8): log task N` commit.
5. **A higher model is always fine; a lower one is not.** A task may run on a model above its segment's. A task that
   needs a *higher* model than the current one is a stop (see "Segments").
6. **Stop and ask the user** (do not guess) when: a test still fails after two honest attempts at a fix; the probe note
   (Task 0) contradicts the plan in a way the plan's own rules do not cover; a step needs a credential, a device or a
   decision only the user has; a package the plan needs has no version that meets the Global Constraints; an
   instruction cannot be followed as written. Log it as `blocked`.
7. **Never fabricate results.** A step is `done` only when its command was run and its stated expectation held.
8. **Report the model honestly.** At the start of each chat, check the model you are running as (your system prompt
   names it) and compare it with the segment you are about to run.

## Segments (where the model changes)

Tasks are grouped so each runs on the cheapest model that can do it well, with as few switches as possible.

| Segment | Tasks | Model | Why |
|---|---|---|---|
| S1 | 0–5 | **Sonnet** | Wire, parsing, the orb painter, the composer, the socket protocols: well specified, test-first |
| S2 | 6–10 | **Opus** | Platform audio, the barge-in state machine, WebRTC, the foreground service: timing bugs and native config |
| S3 | 11–14 | **Sonnet** | Screens and settings built from the design against S2's interfaces |
| S4 | 15–16 | **Haiku** | Demo script, goldens, docs: mechanical |
| S5 | 17–18 | **Sonnet** | Live tests and the device pass (needs the user and a phone) |
| S6 | 19 | **Opus** | Final review of the whole branch |

**At a segment boundary, stop.** When the last task of a segment is committed and logged:

1. Write the log entry `segment S<n> complete`, with the next segment's model and its first task.
2. Commit the log.
3. Tell the user, in these words or close to them:

   > Segment S<n> is done and logged (tasks <a>–<b>). The next segment needs **<Model>** for task <c>. Please open a
   > new chat, switch to <Model> with `/model <name>`, and run `/phase8`. It will read the log and carry on.

4. Stop. Do not start the next segment's first task, even if the current model could do it. At a boundary where the
   current model is *higher* than the next segment needs (S2→S3, S3→S4), still stop, because the user chose cheaper
   models for those tasks; ask once whether to continue on the current model instead.

## Starting or resuming a chat

Do these in order, and say what you found before you act.

1. Read this file, then the progress log, then the plan's header (Global Constraints, Review Focus, file map). Read a
   task's full text only when you start it.
2. Run `git status -sb` and `git log --oneline -8`. Confirm the branch is `feat/phase8-voice`. The only allowed
   uncommitted changes are `android/gradle.properties` and `store/screenshots/`.
3. Compare the log with git: the last `done` task's commit sha must be in `git log`. If they disagree, stop and tell the
   user what differs; do not repair either silently.
4. Find the first task whose status is not `done`.
   - `todo`: start it at its Step 1.
   - `doing`: read its `next step` line in the log, run `git status` and `git diff` to see what is on disk, finish or
     redo that step, then continue. If the working tree holds half-written work you cannot account for, stop and ask.
   - `blocked`: read the reason; if the user has not answered it in this chat, ask again.
5. Check the segment: if this task's segment needs a higher model than you are running as, stop and ask the user to
   switch (the message above), without touching code.
6. Set that task to `doing` in the log (with the start time) before editing code.

## The log

`2026-10-19-phase8-progress.md` has a status table at the top and an append-only journal below it.

- **Status table:** one row per task: `todo`, `doing`, `done` or `blocked`, the commit sha of its last commit, and the
  model it ran on.
- **Journal entry** after each task, appended at the bottom, newest last:

  ```
  ### Task N — <title> — done — <date time> — <model>
  - Commits: <sha> <subject>; <sha> <subject>
  - Verified: <the commands run and what they printed, one line each>
  - Packages: <name version, only when the task added one>
  - Deviations: <where you did something other than the plan says, and why; "none" if none>
  - Decisions for later tasks: <anything the next task must know, such as a renamed type>
  - Next: Task N+1, Step 1
  ```

- **Mid-task checkpoints:** when you stop partway (token pressure, a block, a long wait), write
  `### Task N — doing — <time>` with `Next: Step k` and what is already on disk. Keep it to a few lines.
- **Task 0 and Task 18** also record their results in their own files (the probe note and the device pass), and the
  journal entry links them.
- The log never holds secrets (no tokens, tickets, transcripts, or contents of `~/.iris-live.json`).

## What needs the user, not the model

- **Task 0:** needs `~/.iris-live.json` and the live server; if it is missing, stop and ask. It creates one throwaway
  session and interrupts it.
- **Task 17:** creates a throwaway conversation and writes the server's current voice back to itself. Tell the user
  first and wait for a yes in this chat.
- **Task 18:** the device pass. Stop and ask the user to connect a physical Android phone, ask whether they drive the
  checklist or you drive `adb`, and ask them to switch the server's `voice_chat_mode` to `gpt-live` for the GPT-Live
  part and back afterwards (about $0.05 a minute on their OpenAI key). Log what they chose.
- **Task 19:** ends by pushing the branch and opening the PR, only after the user says so.
