# Push Notifications Implementation Plan

> **For agentic workers:** Execute inline with superpowers:executing-plans (the user's rule: no subagents). Steps use
> checkbox (`- [ ]`) syntax for tracking. Phase 9 run book rules apply (log after each task, commits under the user's
> name only, stop at segment boundaries).

**Goal:** Iris alerts the user, in their own words, when a reply they are waiting for lands, when the agent waits for
their approval, and when a scheduled job finishes, on Android (no Google) and iOS (APNs direct).

**Architecture:** The `hermes-iris` plugin's hooks (agent process) append events to a per-profile on-disk outbox. The
dashboard process, which serves the plugin routes, renders each event per registered device and delivers it: an SSE
stream that Iris's Android foreground service holds open, and a background worker that signs and sends APNs requests
for iPhones. Iris registers the device, marks a chat *active* when the user sends to it, posts notifications (Android),
suppresses ones for the chat on screen, and opens the chat on tap; an approval action opens the chat after unlock and
answers the pending approval there.

**Tech Stack:** Python 3 / FastAPI (plugin), Flutter + Riverpod 3, `flutter_foreground_task` 10.0.0 (already a
dependency), `flutter_local_notifications` (new, Android only), Swift (`AppDelegate` method channel), APNs HTTP/2 with
ES256 token auth.

**Spec:** `docs/superpowers/specs/2026-11-13-push-notifications-design.md` (approved 2026-11-13).

## Global Constraints

- **No Google:** no Firebase/FCM, no Play services, directly or transitively. Every package added is checked with
  `flutter pub deps` (no `firebase`, `google_mobile`, `play_services`) and on Android with
  `./gradlew :app:dependencies --configuration releaseRuntimeClasspath` (no `com.google.firebase`,
  `com.google.android.gms`).
- **No relay:** the server talks to `api.push.apple.com` / `api.sandbox.push.apple.com` directly.
- Plugin code in `server/hermes-iris/`; plugin version becomes **0.4.0** (`plugin.yaml`, `pyproject.toml`,
  `__init__.__version__`, `dashboard/manifest.json`, CHANGELOG).
- Store rules as GenUI: every path component through `safe_component`; atomic 0600 writes; nothing logs content,
  commands, tokens or keys.
- Hooks never raise into the agent and never block on the network (they append to a file and return).
- Events: `reply` (active Iris chat, turn completed or failed, not interrupted), `approval` (active Iris chat),
  `job` (`platform == "cron"`). Each per device: `on` (bool), `text` (the user's words, 1–100 chars), `mode`
  (`content` | `text`).
- Defaults: reply `on`, `"Attention!"`, `text`; approval `on`, `"Attention!"`, `content`; job `on`, `"Attention!"`,
  `content`.
- Mode `text`: the notification shows only the user's text; no content field of the event leaves the server for that
  device. Mode `content`: title = user's text, body = the content line.
- Approval buttons: **Approve once** (`once`) and **Deny** (`deny`); both require the device to be unlocked. Session /
  always stay in the app.
- Active chat: marked by Iris when the user sends to it; cleared when its turn ends; expires after 6 h.
- Android: one foreground service (the existing `flutter_foreground_task` service), type `remoteMessaging` for push
  (manifest `microphone|remoteMessaging`); permanent low-importance "Iris is connected" notification that reads
  "Iris can't reach your server" while disconnected.
- Commits: user's name only; never `git add -A`; never commit `android/gradle.properties` or `store/screenshots/`.

## Decisions made in this plan (not in the spec; the user may overrule)

1. **Approval actions open Iris.** Approve once / Deny are `foreground` actions on both platforms: the OS asks for
   unlock, Iris opens on that chat, fetches pending approvals (`approval.pending`), answers the one the notification
   named, and shows the outcome in the chat (approved / denied / already answered / expired). Answering without
   opening the app would need the dashboard WebSocket protocol re-implemented in Swift and Kotlin; opening reuses the
   tested Dart path and gives unlock on both platforms for free.
2. **Iris marks active chats explicitly** (`POST push/active/{session_id}` on send), rather than the plugin guessing
   from `platform == "desktop"` (the web dashboard uses that platform too).
3. **Device settings live on the server**, so the server can leave content out for `text`-mode devices.
4. **Replay window:** the stream replays events up to 15 min old after `after`; APNs skips events older than 10 min.
   The outbox keeps 24 h / 1,000 events.
5. **iOS notifications are remote only**; `flutter_local_notifications` is used on Android only.
6. A notification already shown for an approval that is answered elsewhere is cancelled on Android
   (`approval_done` event); iOS leaves it, and opening it reports "already answered".

## Review Focus

1. **Dashboard login expires while the Android service runs for days.** Expect: the stream re-authenticates from
   stored credentials and reconnects; the "connected" notification says "can't reach" only while it really can't.
   Test in Task 9 (`reconnects after a 401 by logging in again`).
2. **Two Iris devices, one in `text` mode.** Expect: the `text` device's payload holds no `preview`/`command`/
   `job_name`. Test in Task 3 (`text mode leaks no content`) and Task 6 (APNs body).
3. **Approval answered on another device before the user taps.** Expect: Iris opens the chat and says it was already
   answered; nothing is approved twice. Test in Task 8 (`answer when nothing is pending`).
4. **Voice call starts while push holds the foreground service (and ends).** Expect: the call's notification and mic
   work; after the call the push connection is still up. Test in Task 9 (`call then push share the service`).
5. **The user's text with emoji, quotes or 100+ chars.** Expect: saved trimmed to 100 chars, sent intact in JSON/SSE/
   APNs. Test in Task 2 (`text is trimmed and kept verbatim`).

**Interfaces:**
- Consumes: Task 3's `active`, `outbox`; `docs/superpowers/plans/2026-11-13-push-probe.md` (a), (c) and "Server facts".
- Produces: `hooks.on_post_llm_call(**kw)`, `hooks.on_session_end(**kw)`, `hooks.on_pre_approval_request(**kw)`,
  `hooks.on_post_approval_response(**kw)`; each wraps its body in `try/except Exception` (logged without content) and
  returns `None`. Titles come from the session row through Hermes's session DB if one is reachable; otherwise `title`
  is `None` and render falls back to the user's text.
- Rules from the probe (all hooks run in the agent process; dashboard and cron share nothing in memory):
  - `on_session_end` carries no reply text. `post_llm_call` fires earlier in the same finalizer with the same
    `turn_id` and `assistant_response`, so `on_post_llm_call` keeps `{turn_id: preview}` in memory (cap 50, oldest
    dropped) and `on_session_end` pops it by `turn_id`.
  - `on_session_end` without a `turn_id` is a chat closing, not a turn: ignore it. `interrupted: true` → nothing;
    `failed: true` or `completed: false` → `outcome: "failed"`.
  - `platform == "cron"` → `job`: job id = `task_id.split(":")[1]`; name from `<hermes home>/cron/jobs.json`
    (`{"jobs": [{"id", "name", …}]}`), falling back to the id. Cron runs are not gated on `active`.
  - `pre_approval_request` with `surface == "smart"` is the guardian model's check: ignore it. Only `gateway`/`cli`
    asks become `approval` events. Key = `session_key` (the stored id). `post_approval_response` with a non-`smart`
    surface → `approval_done` (any `choice`, including `timeout`).
  - The approval reaches Iris as an `approval` server request, not an event; approvals expire 300 s after the ask
    (`approvals.timeout`).
