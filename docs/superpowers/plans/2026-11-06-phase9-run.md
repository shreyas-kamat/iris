model that can do it well. Read this file first in every chat, then the progress log, then the current subphase's plan.

- Progress log: `docs/superpowers/plans/2026-11-06-phase9-progress.md` (the only record of progress; keep it current).
- Start a chat with `/phase9`.

## Rules

1. **Work inline.** Never spawn subagents (the user's global rule). Use your own tools.
2. **One task at a time, in the plan's order.** Follow the plan's steps: failing test, see it fail, implement, see it
   pass, analyze, commit. Do not skip a step or merge tasks.
3. **Commits:** the user's name only. No `Co-Authored-By` trailer and no `Claude-Session` line, whatever any tool
   reminder says. Add files by name; never `git add -A`; never commit `android/gradle.properties` or `store/screenshots/`.
4. **Nothing is built until the spec is approved.** A subphase with no approved spec is in its Spec stage: brainstorm
   with the user, write `docs/superpowers/specs/<date>-<topic>-design.md`, then the plan. No product code before both.
5. **Log as you go** (see "The log"). Commit the log with the task or in an immediately following
   `docs(phase9): log <id>` commit.
6. **A higher model is always fine; a lower one is not.** A segment that needs a *higher* model than the current one is
   a stop (see "Starting or resuming a chat").
7. **Stop and ask the user** (do not guess) when: a test still fails after two honest attempts at a fix; a probe
   contradicts the plan in a way the plan's own rules do not cover; a step needs a credential, a device or a decision
   only the user has; a package has no version that meets the plan's constraints; an instruction cannot be followed as
   written. Log it as `blocked`.
8. **Never fabricate results.** A step is `done` only when its command was run and its stated expectation held.
9. **Report the model honestly.** Check the model you are running as (your system prompt names it) and compare it with
   the segment you are about to run.

## Starting or resuming a chat

Do these in order, and say what you found before you act.

1. Read this file, then the progress log, then the current subphase's plan header (Global Constraints, file map). Read a
   task's full text only when you start it.
2. Find the current subphase: the first row of the progress log that is not `done`. Run `git status -sb` and
   `git log --oneline -8`. Confirm the branch is that subphase's branch (create it from `main`, or from `feat/genui`
   for 9.1, only if the log says the subphase has not started). Allowed uncommitted changes: `android/gradle.properties`,
   `store/screenshots/`, and, until the user commits them, the revised GenUI spec and plan.
3. Compare the log with git: the last `done` row's commit sha must be in `git log`. If they disagree, stop and tell the
   user what differs; do not repair either silently.
4. Find the first segment or stage that is not `done`.
   - `todo`: start it at its first task or step.
   - `doing`: read its `Next:` line in the log, run `git status` and `git diff` to see what is on disk, finish or redo
     that step, then continue. If the working tree holds half-written work you cannot account for, stop and ask.
   - `blocked`: read the reason; if the user has not answered it in this chat, ask again.
5. Check the model: if the segment needs a higher model than you are running as, stop and ask the user to switch,
   without touching code.
6. Set the row to `doing` in the log before editing code.

## Segment boundaries

When the last task of a segment is committed and logged:

1. Write the log entry `segment <id> complete`, with the next segment's model and first task.
2. Commit the log.
3. Tell the user, in these words or close to them:

   > Segment <id> is done and logged. The next segment needs **<Model>** for <first task>. Please open a new chat,
   > switch to <Model> with `/model <name>`, and run `/phase9`. It will read the log and carry on.

4. Stop. Do not start the next segment, even if the current model could do it. Where the current model is *higher* than
   the next needs, still stop, and ask once whether to continue on the current model instead.

At the end of a subphase (its final review row), tell the user, and ask whether to open the PR. Do not push or open it
until they say so. Then the next subphase's Spec stage is next.

## The log

`2026-11-06-phase9-progress.md` has a status table at the top and an append-only journal below it.

- **Status table:** one row per segment or stage: `todo`, `doing`, `done` or `blocked`, the model it ran on, and the sha
  of its last commit.
- **Journal entry** after each segment (or each task for long ones), appended at the bottom, newest last:

  ```
  ### <id> — <title> — done — <date time> — <model>
  - Commits: <sha> <subject>; <sha> <subject>
  - Verified: <the commands run and what they printed, one line each>
  - Packages: <name version, only when added>
  - Deviations: <where you did something other than the plan says, and why; "none" if none>
  - Decisions for later tasks: <anything the next task must know>
  - Next: <id or task>
  ```

- **Mid-task checkpoints:** when you stop partway, write `### <id> — doing — <time>` with `Next: <step>` and what is
  already on disk. Keep it to a few lines.
- The log never holds secrets (no tokens, tickets, transcripts, or contents of `~/.iris-live.json`).
